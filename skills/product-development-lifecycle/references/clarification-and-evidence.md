# 需求澄清、证据与反向解释

## 何时应该询问

AI默认先读取现有资料并推进可安全完成的工作。出现以下任一情况时进入“对齐检查点”：

- 无法用一句话说明用户要得到的可观察结果。
- 同一关键词存在会改变范围、成本、动线或验收的多种解释。
- 两项已确认要求互相冲突。
- 缺少不可替代的账号、资产、许可、权限或业务决定。
- 同一个维度已经发生两次实质性修改，说明双方心中的标准仍未显性化。
- 产物虽然能实现，但无法写出用户如何判断它正确。

不要因为存在普通实现选择就发起访谈。可回退的技术细节由AI基于现有约束决定，并在交付中记录。

## 五项质疑法

对任何影响结果的结论，依次检查：

1. **词义**：关键词具体指什么？有哪些可观察边界？
2. **默认前提**：这句话假定了哪些用户、数据、环境、权限或因果关系？
3. **证据**：依据是运行事实、用户确认、外部资料、设计决定还是猜测？证据是否仍然适用？
4. **相反解释**：同一现象还能怎样解释？什么证据能区分它们？
5. **影响**：结论成立或不成立，分别会改变目标、方案、成本、风险和验收中的什么？

提问只保留会改变下一产物的问题。推荐形式：

> 我目前把“X”理解为……，依据是……；另一种解释是……。两种解释会分别导致……。请确认你指的是哪一种。

## 常见含糊词

| 词语 | 必须补充的定义 |
| --- | --- |
| 完整、全部 | 包含的功能清单、明确不包含项、边界情况 |
| 最新 | 截止日期、版本、来源及冲突优先级 |
| 高质量、好看 | 参考原则、目标用户、可读性、层级、品牌和设备标准 |
| 像某产品 | 借鉴功能、动线或信息结构中的哪一部分；哪些品牌资产禁止复制 |
| 可用、完成 | 在哪一层、哪个环境、由什么证据证明 |
| 真实数据 | 来源、授权、版本、质量、覆盖和更新方式 |
| 自动同步 | 谁触发、同步什么、冲突规则、失败恢复和版本兼容 |
| 100%符合 | 显性需求覆盖率、原型确认范围、验收证据和未表达偏好的处理方式 |
| 优先、尽快 | 相对顺序、时间约束、可牺牲与不可牺牲项 |

## 证据标签

| 标签 | 含义 | 使用规则 |
| --- | --- | --- |
| O | 直接观察 | 当前运行、截图、日志、实际用户操作或测量 |
| R | 外部资料 | 官方文档、研究、标准、授权源码或数据；记录版本与日期 |
| D | 设计决定 | 为目标作出的取舍，不冒充外部事实 |
| H | 待验证假设 | 可以推进探索，但不能作为完成证据 |
| X | 反例或相反解释 | 用来限定规则适用范围，避免过度概括 |
| B | 外部阻塞 | 缺少权限、资产、许可、设备或决定；写明最小解除动作 |

证据强度从“存在”到“可证明”不同。源码存在只能证明实现材料存在；自动测试只能证明它覆盖的行为；模拟器只能证明对应模拟环境；真机反馈只覆盖实际操作过的路径；生产结论必须有生产环境证据。

## 多次修改后的对齐检查点

同一维度发生第二次实质修改后，暂停继续堆补丁并产出一页对齐记录：

- 原目标和当前目标是否相同。
- 两次修改分别暴露了什么未表达标准。
- 当前双方使用的参考、关键词和成功标准是否一致。
- 需要先确认高保真原型、数据样例还是技术可行性。
- 哪些已完成工作仍可复用，哪些结论失效。

确认后更新需求契约或原型版本，再继续开发。若修改源自实现错误，修复实现即可，不把它伪装成需求变化。

## 结论的双向影响

重大结论必须至少写一句双向影响：

- **若成立**：采用什么方案，新增什么成本或限制，需要什么验证。
- **若不成立**：回到哪个决策点，哪些工作可省略或必须重做。

这样可以判断一个问题是否真的值得打断用户，也能防止团队围绕无影响的措辞反复讨论。
