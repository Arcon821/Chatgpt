# 产品到开发完整生命周期标准

## 目的

把一个想法逐步变成可验证、可交付、可复用的产品成果。每个阶段都必须产生可审阅的产物和进入下一阶段的条件。已有可靠成果可以直接复用或补证，不要求机械地重做前序阶段。

## 总体闭环

```text
想法 → 需求 → 产品方案 → 高保真原型 → 技术方案
     → 增量开发 → 分层测试 → 发布 → 结果观察 → 复盘回写
                         ↑                         │
                         └──── 有证据的修正 ──────┘
```

| 阶段 | 要回答的问题 | 必要产物 | 通过条件 |
| --- | --- | --- | --- |
| 0 想法与问题 | 谁在什么场景遇到什么问题，为什么现在处理？ | 一页问题陈述、已有证据、未知项 | 问题和方案没有混为一谈；能说明不做的影响 |
| 1 需求契约 | 本次要改变什么，范围在哪里，怎样算完成？ | 目标、用户、场景、范围、约束、验收标准、假设 | 目标可观察；关键含糊词已定义；范围与优先级无冲突 |
| 2 产品方案 | 用户如何从起点完成任务，异常时怎样继续？ | 信息架构、任务流、状态表、数据与权限规则 | 主流程闭环；空/错/加载/禁用/权限状态都有出口 |
| 3 高保真原型 | 基础逻辑、动线、内容层级和视觉是否匹配预期？ | 可交互原型、真实长度文案、主要状态、适配说明 | 用户按验收脚本完成任务；批准范围和未决项被记录 |
| 4 技术方案 | 怎样在现有系统中可靠实现，并可回退？ | 架构、契约、数据模型、模块边界、迁移、风险与测试计划 | 每项需求有实现归属和验证方法；关键风险有处理策略 |
| 5 增量开发 | 怎样尽早交付可运行的完整切片？ | 可运行代码、配置、必要测试、开发记录 | 当前切片从入口到结果可执行；未用假成功掩盖缺失能力 |
| 6 分层验证 | 哪一层已经被什么证据证明？ | 单元/集成/E2E、渲染、设备、环境和人工验收证据 | 验收矩阵逐项有结果；未验证项明确，不跨层推定 |
| 7 发布 | 谁、何时、以何种方式获得版本，失败怎样恢复？ | 发布计划、版本、权限、监控、回退、用户说明 | 生产前置满足；变更可追踪；回退路径经过核对 |
| 8 结果与复盘 | 产品是否解决了原问题，哪些经验可以复用？ | 指标/反馈、偏差分析、经验提案、后续决定 | 事实、决定和假设分开；公共经验有适用边界和审批 |

## 三类基线

每次工作开始先核对三类基线，避免在错误版本上继续：

1. **产品基线**：最新目标、范围、已确认决定、未决问题和验收定义。
2. **工程基线**：当前代码、分支、未提交修改、配置、依赖、部署和测试入口。
3. **证据基线**：用户反馈、运行截图、日志、测试、研究资料，以及各证据的日期和环境。

文档和现实冲突时，先确认更具体、更新且可复查的证据；写纠偏记录，不静默覆盖历史。

## 阶段推进规则

- 一个阶段通过只授权进入下一阶段，不代表最终产品完成。
- 高风险未知项可以先做研究或技术验证；验证结果回到需求或原型决策，不直接变成用户功能。
- 开发按“可完成的用户任务”切片。切片包含入口、输入、状态、结果、退出和必要证据，避免同时铺开大量半成品。
- 需求变更和实现缺陷分别记录：前者改变契约，后者表示实现没有满足契约。
- 外部依赖缺失时标记阻塞及影响范围，同时继续不依赖该前置的工作。

## 完成定义

“完成”是分层结论：

| 层级 | 可声称的结论 |
| --- | --- |
| 需求确认 | 目标、范围和验收标准已达成共识 |
| 原型确认 | 被展示的逻辑、动线、内容和视觉达到确认范围 |
| 代码就绪 | 实现存在且通过对应源码检查 |
| 本地通过 | 在指定本地环境运行并通过测试 |
| 环境通过 | 后端、权限、数据和配置在指定环境验证 |
| 设备通过 | 指定浏览器/设备上完成关键任务 |
| 已发布 | 指定版本实际对目标用户可用 |
| 结果有效 | 发布后的指标或用户反馈支持原问题得到改善 |

低层证据不能代替高层结论。原型通过不证明代码完成，自动测试通过不证明界面可用，历史部署成功不证明当前生产仍正常。

## 角色协作

人负责目标、取舍、价值判断、关键原型确认和公共标准批准。AI负责读取证据、发现含糊与冲突、形成可审阅产物、实施已授权工作、验证并记录边界。AI在可回退的实现细节上主动推进，在改变目标、范围、成本、权限或用户体验的决定前取得确认。
